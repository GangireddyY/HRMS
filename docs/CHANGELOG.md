## [Unreleased]

### Added
- **Slack and Microsoft Teams alerts** (Administration → Integrations → Webhooks & alerts → Add webhook or alert): a webhook can be sent as **Slack** (to an incoming-webhook URL) or **Microsoft Teams** (to a Workflows or connector URL) instead of signed JSON. The events it subscribes to are posted as a chat message: a Slack message with the event, its summary and an "Open HRMS" link, or a Teams adaptive card with the same. They share everything webhooks have: event picker, queue with retries, delivery log, redelivery, test message and switching off after 25 failures. Their URL is a credential, so it is stored encrypted (`url_encrypted`, re-encrypted on key rotation) and only a masked copy (`https://hooks.slack.com/…k3Qz`) is shown or audited; editing keeps it unless a new one is entered. In production the URL must be on Slack's or Microsoft's webhook hosts. No signing secret (rotating one is refused). API: `format: "JSON" | "SLACK" | "TEAMS"` on `POST /integrations/webhooks` (fixed after creation). Migration `20261112160000_chat_webhooks`.
- **Job-board feed:** `GET /careers/:slug/jobs.xml` (public) lists the open public jobs as an XML feed in the Indeed format, which Indeed, Jooble, Adzuna, Careerjet and most aggregators import: title, date, reference, careers-page link, company, city / state / country of the office, description with requirements, job type, team, experience and closing date. Jobs → **Job-board feed** copies the link. Public job pages also carry schema.org `JobPosting` data, so Google for Jobs can list them.
- **Yearly statutory rate updates** (Platform → Statutory rates, platform permission `platform.statutory.manage`; migration `20261112170000_statutory_rates`):
  - **What it is:** PF / ESI rates and each year's income-tax rules are kept as data, so a notification or a Finance Act needs no release.
  - **PF / EPS / ESI:** rates, PF wage ceiling and ESI coverage limit are stored with an "in force from" date. Payroll for a month uses the set in force on its first day, so a change from 1 July leaves June untouched even when June is recalculated. A change can be scheduled ahead and is marked *Upcoming*. Today's rates are seeded.
  - **Income tax:** each financial year's rules (both regimes, separate 60+ / 80+ old-regime slabs, 87A rebate and marginal relief, surcharge bands, cess) can be entered in an editor, replacing the built-in ones. A year without rules of its own uses the latest earlier year's and is flagged *not confirmed*. From February the page reminds platform admins to enter next year's rules before April's payroll. Rules are validated: rising slab limits, an open last slab, sensible rates.
  - **Where they apply:** payroll runs, salary previews and Form 16 use them. Draft runs pick up a change when recalculated; approved payslips keep their figures. Every change is in the platform audit log, and `GET /payroll/statutory-rates?year=&month=` shows a payroll team what applies to a month.
- **User guide** (`docs/USER_GUIDE.md`): task-by-task help for employees, managers, HR staff and administrators (where to click, what happens next, the monthly payroll cycle, hiring to exit, common problems).
- **Design decisions** (`docs/DECISIONS.md`): twelve architecture decision records (modular monolith, shared contracts, three-layer tenant isolation, field encryption, PostgreSQL job queue, audit log as event stream, approval snapshots, token handling, provider adapters, SQL migrations, one app for web and phone, chat alerts as webhook formats).
- **Phone app for Android and iOS** (Capacitor, `frontend/android`, `frontend/ios`; guide in `docs/MOBILE.md`):
  - **App:** a store app around the hosted HRMS site (`HRMS_APP_URL`), so sign-in stays as secure as on the web and every deploy reaches phones. Inside the app, the Android back button navigates back, links to the HRMS site and notification taps open in the app, and punch-in asks for location through the phone's permission prompt.
  - **Notifications:** the app registers for push on sign-in and unregisters on sign-out (`POST /notifications/push/native` · `…/remove`). The API sends to Android through Firebase Cloud Messaging (`FCM_CREDENTIALS_FILE`) and to iPhones through APNs with token auth (`APNS_KEY_FILE`, `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_TOPIC`), following the same preferences as browser notifications. An install that another person signs in on moves to them, and devices the push service reports gone are removed. Migration `20261112150000_native_push_tokens`.
  - **Builds:** release signing and version come from Gradle properties, never git. CI builds an Android debug APK on every run and compiles the iOS project on `main`. The frontend image serves `/.well-known/` (app link verification files) from a mounted directory.
- **Tally accounting export** (Payroll setup → Accounting (Tally); a payroll run's Downloads → Accounting journal):
  - **Journal:** an approved or paid run becomes one balanced journal voucher dated the last day of the month. Earnings and employer contributions are debited; deductions, employer PF / ESI / LWF dues and net salary are credited. Loans, benefits and one-off deductions go to their own ledgers, and lines on the same ledger are netted. Optionally, salary and employer cost are split by department as Tally cost centres.
  - **Ledgers:** every posting has a default ledger name that can be renamed to match the chart of accounts, and individual earnings (HRA, bonus, arrears…) can go to their own expense ledger.
  - **Files:** preview the journal, then download Tally import XML for the voucher (Gateway → Import → Vouchers) and for the ledger and cost-centre masters it uses (created under Indirect Expenses, Duties & Taxes, Current Liabilities or Loans & Advances). The voucher carries the run's id, so Tally refuses importing the same run twice. Exports are audited. Migration `20261112140000_accounting_settings`.
- **Approval chains everywhere**:
  - **Coverage:** configurable chains now also decide travel requests, resignations (each step accepts; the last one sets the last working day) and job offers (matched on CTC and department; the requisition's hiring manager is "the manager"). A matching offer chain makes approval required. Withdrawing a resignation, changing or withdrawing an offer, or cancelling a trip closes its chain.
  - **My approvals** (My Workspace → My approvals, `GET /approvals/waiting`): every chain step waiting for you, whatever the kind, with what's needed to decide, approved or rejected right there. Named approvers who hold no module role can act this way too.
  - **Notifications and counts:** chain notifications link to My approvals. The dashboard counts include chain steps (and offers), and every request detail shows the chain's progress.
- **Notification digests and WhatsApp** (Notifications → settings):
  - **Digests:** choose a daily or weekly summary instead of one email per notification, at your local hour (and weekday). It lists what you haven't read since the last one, grouped by organization. Grievance items carry no details.
  - **WhatsApp:** add your number and confirm it with a 6-digit code sent there (3 codes an hour, 5 tries, hashed, 10 minutes). Notifications in your email categories are then sent as a WhatsApp template message (title and link) through the WhatsApp Business Cloud API (`WHATSAPP_PROVIDER=meta`), or written to the log in development.
- **Scheduled reports** (Report builder → Scheduled emails): email a saved report daily, weekly or monthly at a local hour, as Excel or CSV, to members of the organization. Each recipient gets only the rows their own access allows, and anyone without report export rights or access to the data is skipped (shown on the schedule). Dated reports cover a rolling period (yesterday, last week, last month, month to date, last 30 days). You can send one now, pause it or edit it.
- **Calendar invites and feeds**:
  - **Invites:** approved leave (all-day, out of office), interviews (candidate and panel) and 1:1s are emailed as iCalendar invites. Calendars add them, update them when they change (same UID, rising sequence) and remove them when cancelled. Removed panelists get a cancellation. People can switch invites off.
  - **Calendar subscription:** a private feed URL (Notifications → settings) for Google Calendar, Outlook or Apple Calendar. It has your leave, your team's leave, 1:1s, interviews you sit on and holidays. Only the URL's hash is stored, and it can be replaced or switched off.
- **Compensation budgets** (Salary increases → Department pools): split a cycle's increase money into a pool per department, suggested from the department's payroll and the cycle's budget %. Each pool shows what's planned and committed. Approving an increase that would overspend its pool needs an explicit, audited override.
- **Succession planning** (HR Operations → Performance → Succession, new `performance.succession.view` / `.manage` permissions):
  - **Plans:** critical roles (held by someone, or vacant) record how critical they are and the risk of losing the holder, with a ranked bench of successors, their readiness (now, in 1 to 2 years, in 3+), development notes and 9-box placement from their latest review.
  - **Bench strength:** each plan shows whether a successor is ready, at risk or missing. HR manages plans; department managers see the plans in their department, never the one for their own role.
- **Legal entities and currencies** (Administration → Entities & currencies):
  - **Entities:** the companies you employ people through, each with its country, currency and registrations, and one default. Employees and pay groups belong to an entity.
  - **Payroll:** payslips are in the paying entity's currency (screens and PDF), and Indian statutory deductions (PF, ESI, PT, LWF, TDS) apply only to entities in India.
  - **Exchange rates:** dated rates into the base currency. Expense receipts in another currency are converted at the rate on the expense date (receipt amount and rate kept). The report builder's payslips gain the currency and net pay in the base currency for consolidated figures.
- **AI assistant** (opt-in per organization): with an OpenAI-compatible provider configured (`ASSISTANT_PROVIDER=openai`: OpenAI, Azure OpenAI, OpenRouter, vLLM or Ollama) and an admin's consent, the assistant answers free-form questions and policy questions.
  - **Grounding:** it reads only through tools run with the person's own access: profile, leave, holidays, policies, payslips, approvals, team leave and colleagues. It's told to answer only from their results, and links only to app pages.
  - **Fallback:** without a provider, with the switch off, or when the provider fails, the built-in keyword assistant answers as before.
- **Single sign-on (OpenID Connect)** (Organization settings → Single sign-on): connect any OIDC provider (Microsoft Entra ID, Google Workspace, Okta, Keycloak…) with its issuer URL, client ID and secret (stored encrypted), for chosen email domains.
  - **Sign-in:** people choose "Sign in with SSO" and enter their work email. The sign-in uses the authorization-code flow with PKCE, a single-use state and a nonce, and the ID token's signature, issuer, audience and expiry are checked.
  - **Matching people:** people are matched to their membership by verified email, and a pending invitation is accepted on the way. With "add new people automatically", someone from an allowed domain joins with a chosen role (within the plan's seats).
  - **Requiring SSO:** with SSO required, members can't use a password, while organization admins keep theirs as a fallback.
  - **Step-up:** an SSO sign-in counts as a fresh step-up.
- **API keys** (Administration → Integrations, new `integration.manage` permission):
  - **Access:** read-only keys for reporting tools and scripts (`Authorization: Bearer hrms_…`). A key can call GET endpoints only, with view permissions its creator chooses and holds, and acts as its creator: if they lose a permission or leave, so does the key.
  - **Safety:** the key is shown once and only its hash is stored. Keys show their last use, can expire, can be revoked, and never pass a step-up.
- **Webhooks**:
  - **Events:** the organization's events (every audited action, e.g. `employee.created`, `leave.request_approved`, `exit.settlement_paid`) are POSTed as JSON to subscribed endpoints, by module (`leave.*`), everything, or exact events. Sign-ins, grievances, privacy and integration changes are never sent.
  - **Signing:** each request is signed (`X-HRMS-Signature: t=…,v1=HMAC-SHA256`). The secret is shown once and can be rotated.
  - **Delivery:** deliveries are queued with the change, retried with backoff, logged with the response, and can be redelivered or test-pinged. An endpoint failing 25 times in a row is switched off. In production endpoints must be HTTPS and can't point at private networks.
- **Custom employee fields** (Administration → Custom fields, new `employee.fields.manage` permission, which HR roles have):
  - **Definitions:** fields are text, long text, number, date, yes/no, one or several choices, email or web address. They're grouped in sections and ordered.
  - **Options:** a field can be required, sensitive (seen only with access to bank and statutory details, and by the employee), or filled in by employees themselves on My profile.
  - **Values:** values are checked against their type and shown on the employee's profile under "Additional details". Changes are audited, without the values of sensitive fields. Archiving a field hides it and keeps its values.
- **Report builder** (Reports → Report builder):
  - **Building a report:** pick a dataset (employees with custom fields, leave requests, attendance, expense claims, payslips), the columns, and filters (is, is one of, contains, at least / at most, empty). Sort it, or summarize it with one row per value, a count and totals.
  - **Preview and export:** the preview shows 500 rows; CSV or Excel exports take up to 20,000 and are audited.
  - **Saving:** reports can be saved and shared with the organization.
  - **Access:** every dataset is limited to what the person may see with that module's permission and scope (managers see their team; payslips need payroll reporting access), and sensitive custom fields only appear for organization-wide sensitive access.
- **Bulk import per module** (HR Operations → People → Bulk import, `/imports`):
  - **What can be imported:** opening leave balances or corrections, salaries (CTC from a date, with the structure and PF), assets (optionally handed over to someone), and custom employee field values. Each import is offered only to people with that module's permissions.
  - **Templates:** each import has a downloadable template. Employees are matched by `employee_code` (case-insensitive), and leave types, salary structures and locations by name or code.
  - **Checking first:** the whole file is checked first and every problem is listed by row and column. Nothing is saved until every row is valid (up to 5,000 rows and 10 MB).
  - **Applying:** rows are applied through the same rules as the screens (audited, notified). Salary raises above the approval threshold go for approval, and rows refused when saving are reported back.
- **Billing (manual)** (Platform → Billing, new `platform.billing.manage` permission):
  - **Subscription terms:** each organization's subscription sets its status (trial, active, cancelled), billing cycle (monthly, quarterly, yearly), seat limit and monthly price (both default to the plan's), discount, GST rate, payment terms, trial end and billing contact. The seat limit applies to invitations and SSO sign-ups.
  - **Invoices:** an invoice is drafted for the next period, with the plan for the cycle plus extra lines or credits, then the discount and tax. It's then issued: numbered `INV-2026-0001`, the bill-to is fixed, it's due after the payment terms, and the subscription moves on a period. Issued invoices are emailed as a PDF to the billing contact, and members who can see billing are notified.
  - **Payments:** payments received (bank transfer, UPI, cheque…) are recorded in full or in part, and an organization's first payment ends its trial. An invoice can be voided until a payment is recorded, which reopens its period.
  - **Overview:** monthly recurring revenue, outstanding and overdue amounts, collections this month, every organization's subscription and all invoices.
  - **For organizations** (Organization settings → Billing & invoices, new `billing.view` / `billing.manage` permissions): organizations see their charge, balance, overdue amounts and next invoice, open each invoice with its payments, download PDFs, and keep their billing contact and GSTIN up to date.
- **Notification emails**: workflow notifications (leave, attendance, payroll, performance, hiring, policies, exit…) are also emailed, queued with the change so nothing is sent if it rolls back. Everyone chooses what they get under Notifications → Email settings (all off, or per category; announcements and surveys are off by default). Grievance emails never include case details; security alerts are always sent.
- **Holidays per location**: a holiday applies to every location or only the chosen ones (regional holidays); attendance, leave day counts, timesheets and payroll use the holidays of each person's location. Official holidays can be imported for chosen locations.
- **Approval cover** (Account → Approval cover, `/approvals/delegations`): someone who approves for a team hands those approvals (leave and comp-off, attendance corrections / work from home / overtime, timesheets, expense claims) to a colleague for up to 90 days. The colleague sees the team's requests marked "on behalf of", is notified of new ones, can decline; never the delegator's own requests, never payroll, salary or loan approvals, no chains. Applied centrally in the access layer (`AuthContext.delegated`, `EmployeeScopeService`).
- **Two-level leave approval**: per leave type, the manager approves and then HR (someone with department- or organization-wide reach, not the first approver) — for every request or only above a number of days. Requests show their step and who approved; the balance is used once, at the final approval; any approver in scope can reject.
- **Offers: approval, letters, e-signature and pre-joining**:
  - **Approval:** optional for every offer (Recruitment → Offers & letters), always above the requisition's budget; the new `recruitment.offer.approve` permission (not for recruiters), never by whoever drafted the offer, and any change needs approving again.
  - **Letter:** the offer letter comes from an editable template with placeholders and a live preview. It is frozen and hashed at release, so what the candidate signs can't change.
  - **Signing:** the candidate gets a private emailed link (only its hash is stored; it can be reissued) to read the letter and sign by typing their name (time, IP, browser and document hash recorded), or decline.
  - **Pre-joining:** after accepting, the same link is the pre-joining portal for personal details (encrypted) and documents. On hire they become the employee's record and documents.
- **India statutory payroll**:
  - **Investment proofs (Form 12BB):** employees upload proofs per section (80C, 80CCD(1B), 80D, rent, home-loan interest) under Salary & tax. Payroll accepts each, fully or in part, or rejects it under Payroll → Tax proofs & returns. From the cut-off month set in payroll setup, monthly TDS uses accepted amounts only, and the payslip warns when declared deductions aren't proven. Employees can print their Form 12BB.
  - **Labour welfare fund:** state-wise rates in the collection months (15 states), employee and employer, on payslips and in the register.
  - **Returns:** the ESIC monthly contribution file (ESI insurance number added to statutory details), and professional tax and LWF per employee and state, both from the run's downloads.
  - **Annual tax:** 24Q deductee details per quarter and Form 16 Part B per employee, which employees can also download themselves. Exports that show PANs need a fresh step-up.
- **Employee services** — three new modules (Growth: assets and helpdesk; Enterprise: all three):
  - **Assets:** a register of company equipment (tags AST-0001…, serial numbers, cost, warranty, location) with every hand-over and return and the condition both ways. Employees see what they hold under My assets, confirm receipt and request equipment; HR hands requests over from stock. Managers see what their team holds. An exit can't be completed while the person still holds an asset, and the exit's clearance lists them.
  - **HR helpdesk:** employees ask HR under HR helpdesk and follow the conversation. Agents (`helpdesk.manage`) work a queue sorted by resolution target (per priority: 8 hours urgent to 5 days low), assign tickets, reply or leave internal notes, and resolve them; employees rate resolved tickets, and resolved tickets close by themselves after 7 days. Agents never handle their own tickets. The queue shows first-reply time, share within target and rating.
  - **Business travel:** employees request trips (purpose, route, dates, mode, hotel, estimate and an optional advance). The manager — or whoever covers their approvals — approves; the travel desk (`travel.manage`) records bookings and pays the advance, and the traveller is told at each step.
- **Payroll extras**:
  - **Arrears:** a salary revision can now be back-dated into months already paid (up to 12 months). The next run works out each paid month again with the new salary and the same loss-of-pay days and pays the difference as "Salary arrears" (taxable, with PF and ESI on the wage part), once. A back-dated cut is flagged on the payslip instead of being recovered automatically.
  - **Bonuses and incentives:** add one to everyone in a draft run (or chosen people) as a fixed amount, a percentage of monthly Basic or gross, or the statutory bonus under the Payment of Bonus Act (Basic up to ₹21,000; 8.33–20% of min(Basic, ₹7,000) per month worked this financial year).
  - **Pay groups:** people can be paid in their own monthly runs (contractors, a subsidiary). Each group's runs are processed and approved separately; nobody is paid by two runs for the same month, and people can't change group while their run is in progress.
  - **Bank file layouts:** besides the standard CSV, HDFC, ICICI, SBI and Axis bulk-upload layouts (internal transfer or NEFT chosen from the IFSC). Check the bank's current template before the first upload.
  - **PDF payslips:** download any payslip as a PDF (net pay in words). Payroll setup can email every payslip as a PDF when a run is approved, optionally opening with the date of birth.
- **Shift swaps**: employees ask a colleague to trade shifts (or a shift for a day off) on a future day from My attendance; the colleague agrees or declines, then the manager — or whoever covers their approvals — approves under Attendance approvals → Shift swaps, which rosters each onto the other's shift. If either roster changed in the meantime, the approval is refused.
- **Office networks and punch photos** (per location, under Organization → Locations): web punch-ins can be limited to the office's IP addresses or ranges (work-from-home days are exempt), and a location can ask for a camera photo with every punch-in. The punch card shows whether you're on the office network; managers and HR open the photo from the attendance register. Photos are deleted when a former employee's personal data is erased.
- **Leave policy rules**: a leave type can apply only to some locations, employment types or grades (as well as by gender); others don't see it or get its balance. Accrual can stop at a balance cap; a month skipped at the cap isn't credited later.
- **Nightly leave job**: accruals, carry-forward and lapse at the start of the leave year, and comp-off expiry are brought up to date every night from 1:00 local time (once per organization, even with several servers), as well as whenever balances are read.
- **Leave encashment through payroll**: employees ask to encash unused days of encashable types under My leave, within the type's yearly limit and keeping its minimum balance. HR approves under Leave balances; the days leave the balance and the next payroll run pays them as a taxable earning (Basic ÷ 26, Basic ÷ 30 or gross ÷ 30, set in payroll setup). Held salaries and cancelled runs release them for the next run.
- **OKRs** (My Workspace → OKRs; HR Operations → OKRs):
  - **Levels:** company objectives (organization-wide `performance.okr.manage`, which HR roles have), department objectives (department managers for their own department) and individual objectives (yours, or those of people you review).
  - **Structure:** objectives align to an objective at the same or a higher level in an overlapping period, never in a loop. Each has up to 8 weighted key results, measured as a number, percentage, amount or done/not-done milestone.
  - **Check-ins:** a check-in records the current value, a confidence (on track / at risk / off track) and a note. It updates the objective's weighted progress and health, and tells the owner.
  - **Browsing:** everyone sees the quarter's OKRs as a tree, filtered by level or "mine", with each key result's check-in history.
- **1:1s** (My Workspace → 1:1s):
  - **Scheduling:** managers schedule 1:1s with the people they review. The team view shows each report's last and next 1:1, highlighting anyone not seen for weeks.
  - **Agenda and notes:** both people add agenda topics, agree actions (owner and due date) and keep shared notes. The manager also has private notes that only they see, and HR doesn't see 1:1s.
  - **Follow-up:** marking a 1:1 as held can book the next one, carrying open topics and actions over. Moving or cancelling notifies the employee.
- **Calibration and the 9-box** (Review cycle → Calibration & 9-box):
  - **Target curve:** a cycle can set a target rating curve (shares adding up to 100%; otherwise the suggested 5/15/50/20/10 bell curve). It can be tuned while the cycle runs.
  - **Calibration view:** HR sees completed ratings against that curve (people above or below the target count per rating), filtered by department. It places everyone on a 9-box of rating × potential and calibrates ratings from one table.
  - **Potential:** reviewers or HR set potential (low / medium / high) once the manager review is in; the employee never sees it.
- **Expense policies** (Payroll setup → Expense policy):
  - **Rules per category:** whether it can be claimed, a limit per claim, a monthly limit (counting pending, approved and paid claims by expense date), and the amount above which a receipt is required (0 = always).
  - **Enforcement:** claims are checked when submitted, with the monthly limit checked one claim at a time per person. The claim form shows the limits and what's left in the month, and asks for the receipt before submitting.
- **Finance approval for large claims**:
  - **Two steps:** above an amount set in the expense policy, a claim the manager approves goes on to finance, under Reimbursements → Finance approval. It needs the new `payroll.reimbursement.finance` permission (the Finance Manager role) and someone other than whoever gave the first approval.
  - **Trail and visibility:** every claim keeps its approval trail (who approved or rejected at each step, with notes). Approvers see the employee's total for the month against the limit, and employees see "With finance" while it waits.
- **Settlement payouts** (Exits → Settlement payouts): approved full & final settlements are listed with their due date and whether the employee has bank details.
  - **Bank file:** finance downloads a transfer file for the chosen settlements (or all) in the standard, HDFC, ICICI, SBI or Axis layout. It needs `payroll.disburse` and a fresh step-up, and every export is audited.
  - **Marking paid:** settlements are then marked paid together with the transfer reference. Each employee is notified, and any that couldn't be marked are reported back.
- **Compensatory off**: mark a leave type as comp-off (validity in days; the recommended set adds "Compensatory off", 90 days). People who worked a holiday or weekly off ask for the day back from My leave (a full shift earns a day, half a shift half a day, within 30 days); approvers decide under Leave requests → Comp-off; approval credits the balance and each credit expires on its own.

- **Browser notifications (Web Push):** people turn them on per browser under Notifications → settings. Each notification is then pushed to their browsers through the job queue, even when HRMS isn't open, for the same kinds they get by email. There's an account-wide switch as well. Grievance pushes carry no case details. Clicking a notification opens the page in an existing tab, or a new one. Browsers whose push service reports them gone (404/410) are dropped. Set up with `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY`.

### Changed
- **One request for approval counts:** the HR dashboard, account home and assistant get every approval count from one request (`GET /dashboard/approvals`) instead of up to 19. The counts come from each module's own list logic, so scopes and approval cover match the lists, and a source that fails is marked instead of failing them all.
- **Fixes from the consistency review:** the POSH report table scrolls instead of clipping on narrow screens, and statutory bonus amounts use the region's number format.
- **Payroll service split:** `payroll-runs.service.ts` (1,534 lines) is now four parts: `PayrollCalculationService` (payslip calculation, arrears), `PayslipsService` (access, PDF, emailed copies), `PayrollExportsService` (register, bank file, PF ECR) and the run workflow, plus `payroll-period.ts` and `payroll-recipients.ts` helpers. Behaviour is unchanged.
- **Review page split:** the performance review page's stepper and next-step bar (`ReviewWorkflowCard`) and side panels (`ReviewSidebar`) are separate components.

### Operations
- **Metrics:** Prometheus metrics at `GET /api/v1/metrics`, protected by `METRICS_TOKEN` (required in production). They cover HTTP requests and latency by route pattern, background job outcomes and backlog, failed sign-ins, and process and event-loop metrics. Alert rules ship in `deploy/prometheus/alerts.yml`: instance down, error rate, latency, failed jobs, job backlog, sign-in attacks, memory and event-loop lag.
- **Tracing:** optional OpenTelemetry tracing (set `OTEL_EXPORTER_OTLP_ENDPOINT`) of HTTP, Express, PostgreSQL and Redis spans, without request bodies or SQL parameters.
- **Scripted backups:** `scripts/db-backup.sh` takes a custom-format dump with a checksum, optionally GPG-encrypted and copied to S3. `scripts/db-restore-verify.sh` restores a dump into a scratch database and checks the migration count and key-table row counts against the source. CI backs up and restores the test database on every build. The dump runs with `--enable-row-security`, because `pg_dump` otherwise refuses to read tables with forced row-level security when connected as a non-superuser owner.
- **Commit messages:** Conventional Commits are checked by commitlint in CI for every commit in a pull request; `npm run hooks:install` checks them locally too.
- **Coverage gates:** CI fails when unit-test coverage drops. Backend (`npm run test:cov`): 19% lines, 8% branches, 10% functions; most backend behaviour is covered by the API end-to-end suite instead. Frontend (`npm run test:cov`, `@vitest/coverage-v8`): TypeScript logic only, since pages are covered by Playwright; 28% lines, 77% branches, 54% functions. Thresholds sit at the current level and only go up.

### Security
- **Breached passwords are refused:** new passwords (sign-up, reset, change, invitation) are checked against Have I Been Pwned's breached-password corpus with k-anonymity: only the first five characters of the SHA-1 are sent, with response padding. If the service doesn't answer in 2.5 s the check is skipped. Turn it off with `PASSWORD_BREACH_CHECK=false`.
- **Row-level security:** PostgreSQL row-level security on all 137 organization-owned tables, enforced behind the ORM tenant hooks. Before each statement the API sets `app.organization_id` on its connection, transaction-local inside transactions and sent only when it changes. The setting is the request's organization, or empty for statements that opt out of tenant scoping (identity, platform, jobs). Rows of other organizations can then be neither read nor written, including through raw SQL and nested includes. Policies are forced on the table owner too. A test checks that every tenant table is covered.
- **Immutable log archives:** audit and login-history archives are stored write-once for `AUDIT_ARCHIVE_RETENTION_DAYS` (7 years by default; required in production) using S3 Object Lock (`AUDIT_ARCHIVE_LOCK_MODE`, COMPLIANCE by default) with a SHA-256 checksum. Until then not even the API's own credentials can delete or overwrite them. The archive shows its "write-once until" date, and the local driver enforces the same rule.
- **KMS envelope encryption:** with `DATA_ENCRYPTION_KEY_SOURCE=aws-kms`, the configuration holds only KMS-encrypted data keys (current and previous). The API and `db:reencrypt` decrypt them at startup through AWS KMS with a fixed encryption context, and startup fails clearly if KMS refuses.
- **Email logs hide tokens:** emails written to the development log no longer include link query strings, which carry one-time reset and invitation tokens. Set `MAIL_LOG_LINKS=true` locally to see them.
- **Approvers need the approve permission:** being an approver on an approval chain is no longer enough on its own. The person must also hold that request's approve permission at any scope: `leave.approve`, `payroll.reimbursement.approve` / `…finance`, `travel.approve`, `exit.approve` or `recruitment.offer.approve`. The approve and reject routes of leave, travel and offers require it again. Saving a chain that names someone without it is refused. People without it are left out of a step when a request starts, and a step left with nobody is skipped; this includes managers on offer chains, since Department Manager doesn't include offer approval by default. Anyone who loses the permission can't decide, and the request is no longer in their **My approvals**.

### Fixed
- The production `Permissions-Policy` allowed no camera access, which blocked photo punches; the camera is now allowed for the app's own origin.
- The sidebar highlights only the most specific matching link (e.g. "OKRs", not "Performance" as well).
- The re-encrypt job (`db:reencrypt`) handles tables keyed by something other than `id` (the SSO client secret, keyed by organization), so it no longer stops at that table.
- Payroll calculation no longer runs several queries at once on its transaction (deprecated in the database driver).

- The backend reads the database connection from `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` (plus optional `DB_SSL`) instead of a single `DATABASE_URL`. Applies to the API, the migration CLI, tests, CI and docker-compose. Update existing `backend/.env` / `.env.test` files accordingly.
- Production boot refuses `DB_USER=postgres` (the superuser).
- The test-database guard checks `DB_NAME` (must contain "test").

## [0.3.1] – 2026-11-04 – Two self-contained applications

### Changed
- `packages/shared` removed. The contracts (permission catalog, role templates, API envelope & error codes, password rules) now live in `backend/src/contracts`; the backend imports them relatively and the frontend compiles the same files through the `@contracts` alias, so there is still a single source of truth. Their tests run in the backend unit suite.
- npm workspaces removed: `backend/` and `frontend/` are independent npm projects with their own `node_modules` and `package-lock.json`. The root `package.json` has no dependencies and only forwards scripts (`install:all`, `dev:backend`, `dev:frontend`, `build`, `typecheck`, `test`, …). The combined `npm run dev` was dropped; start backend and frontend in separate terminals.
- Docker: the backend image builds from the `backend/` context; the frontend image still uses the repository root (it needs `backend/src/contracts`). CI installs each project with `npm ci --prefix <app>`.
- `backend/tsconfig.json` uses `Node16` module resolution and no `baseUrl` (both flagged as deprecated by TypeScript 6).

### Security
- Added `.dockerignore` files: local `.env` secrets, `node_modules` and build output no longer enter Docker build contexts.

## [0.3.0] – 2026-11-04 – Frontend structure, component library & themes

### Added
- **Color themes**: Indigo (default), Ocean, Emerald, Violet, Rose, Amber, Slate, combined with light / dark / system mode. Brand colors are CSS variables (`app/styles/themes.css`) behind Tailwind's `brand-*` utilities, so all components follow the active theme; sidebar tint and focus ring derive from it. Preferences persist per browser and are applied before first paint.
- `core/theme/` (theme catalog, `useThemeStore`, `useThemePalette` for charts, `ThemeSwitcher`), a topbar light/dark toggle, a quick switcher in the account menu, and **My Workspace → Appearance** (`/me/appearance`) with a live preview.
- `@/shared/components` barrel exporting the whole UI library.
- Tests: theme store unit tests; Playwright `appearance.spec.ts` (switch, persist across reload, reset, account-menu switcher).

### Changed
- Frontend reorganized into `app/` (router, styles), `core/` (http, auth, navigation, theme), `shared/` (components grouped as forms / data / feedback / layout, composables, stores, utils), `layouts/` (+ `shell/`) and feature `modules/<domain>/` folders with their own `api/`, `types.ts`, `<domain>.routes.ts`, `pages/` and `components/`.
- The single `api/endpoints.ts` / `api/types.ts` were split per module (`authApi`, `usersApi`, `rolesApi`, `organizationApi`, `auditApi`, `notificationsApi`, `platformApi`); `ListQuery` moved to `core/http/http-client.ts`.
- Consistent naming: `App*` prefix for every shared component (`FormField` → `AppFormField`, `DataTable` → `AppDataTable`, `StatCard` → `AppStatCard`, `ConfirmHost` → `AppConfirmDialog`, `ToastHost` → `AppToaster`, …), `*.store.ts`, `use-*.ts`, `*.api.ts`, `*.routes.ts`; `LoginActivityChart` → `SignInActivityChart`, `MyHomePage` → `AccountHomePage`, `AdminDashboardPage` → `OrganizationDashboardPage`.
- Theme state moved out of the UI store into the theme store; the UI store now only holds shell state.

## [0.2.0] – 2026-11-04 – Restructure & ORM change

### Changed
- Repository layout: `apps/api` → `backend/` (`@hrms/backend`), `apps/web` → `frontend/` (`@hrms/frontend`); `packages/shared` unchanged.
- ORM: **Prisma replaced by Sequelize 6.37 + sequelize-typescript 2.1** (pg driver). Models live in `backend/src/database/models`; the database schema is unchanged.
- Migrations: Prisma Migrate replaced by plain SQL migrations run with **Umzug** (`backend/src/database/migrations/*.up.sql|*.down.sql`, tracked in `schema_migrations`), with `up`, `down`, `status` and `baseline` commands (`baseline` adopts databases created by the Prisma migrations without running SQL).
- Tenant isolation: the Prisma client extension is replaced by Sequelize hooks on tenant models — scoping is now the **default** for every query on those models, and identity/platform/bootstrap paths opt out explicitly with `skipTenantScope: true`. Cross-tenant creates, saves and bulk updates are rejected; queries without a tenant context fail closed.
- Production release step: `node dist/database/migrate.js up && node dist/cli/bootstrap.js`.
- `User` default scope hides password hashes and MFA secrets.

### Fixed
- Audit diffs are computed from cloned snapshots (Sequelize returns live `dataValues` from `get({ plain: true })`).

## [0.1.0] – 2026-11-04 – Phase 1: Foundation

### Added
- Monorepo (npm workspaces): `apps/api` (NestJS 11, Prisma 6), `apps/web` (Vue 3.5, Vite 7, Tailwind 4), `packages/shared` (contracts).
- PostgreSQL schema & migrations: identity, sessions, rotating refresh tokens, action tokens, password history, MFA recovery codes, login events, plans/features, organizations, entitlement overrides, security policies, memberships, permissions, roles, role permissions, membership roles, audit logs (append-only trigger), notifications.
- Authentication: login with lockout, TOTP MFA with recovery codes and replay protection, refresh-token rotation with reuse detection, session management, login history, forgot/reset password, invitations, change password, organization switching, organization-mandated MFA and password expiry (restricted sessions).
- Multi-tenancy: tenant-scoped Prisma client (auto-scoping, fail-closed), composite tenant foreign keys, membership validation per request, organization lifecycle with session revocation.
- Plans & entitlements with per-organization overrides and user limits; self-service and platform-provisioned organizations.
- RBAC: 92-permission catalog across 15 modules, 11 organization role templates + platform Super Admin, record scopes, custom roles, locked roles, privilege-escalation prevention, restricted POSH permission, last-admin guard, catalog sync on boot.
- Audit trail with redacted diffs; organization and platform audit views; organization login history.
- In-app notifications.
- Web: design system, four workspace layouts, permission-filtered navigation, global search, notification bell, light/dark themes, auth pages, self-service, administration, HR dashboard and platform administration pages.
- Tests: Vitest (shared, web), Jest unit + Supertest integration on PostgreSQL (API), Playwright E2E.
- Dockerfiles, docker-compose stack (Postgres, Redis, Mailpit, MinIO), GitHub Actions CI, production bootstrap CLI.
- Documentation: PRD, FRD, ARCHITECTURE, DATABASE, API, RBAC (generated matrix), SECURITY, DEPLOYMENT, TESTING.

### Security
- Audit-log redaction no longer masks non-secret fields that merely resemble sensitive names (e.g. `passwordMinLength`, `companySize`).
- Recruiter template no longer includes `recruitment.requisition.approve` (segregation of duties).
